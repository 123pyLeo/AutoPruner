# 两种开源用法的验收结论（2026-10-30）

> 这是公开发布前的检查记录。当前可用内容和下载入口以 [README](../README.md) 与 [权重索引](../models/README.md) 为准；下文保留检查当时的状态。

**可以把完整框架与 OFT 示例作为本次发布基础；目前还不能把“三类权重都能直接下载运行”或“任意 VLA 裸权重接上 API 就能剪”作为交付承诺。** 这两项分别缺什么，下面分开说明。

机器可读证据、文件哈希和测试范围见 `provenance/night_review_20261030.json`。权重准备索引见 [models/manifest.json](../models/manifest.json)。这些记录不会把模拟分数、训练 loss 或文件存在当作机器人性能证明。

## 用法一：照 OFT 例子使用，再下载我们的三类权重

| 项目 | 实际检查到哪一步 | 能否现在称为完整交付 |
|---|---|---|
| OFT 示例 | 已有真实 API 搜索、恢复、闭环评估、选方案、物理导出和独立动作核对；新增自动收尾 | 使用流程已接通；仍需正常预算效果验证，不保证任意目标都可达成 |
| OFT Object 论文权重 | 从论文评测脚本所记录的恢复目录取 step 10000；已生成自包含 4 层物理模型、模型说明、来源声明和校验值；同输入重载误差 0；本轮十任务各一次为 9/10 | 技术交付物已在本地准备好，尚未托管成公开下载 |
| StarVLA Object 权重 | 完整文件、配置和统计存在；原环境严格参数匹配，生成有限动作；公开固定上游加参考组件也能严格加载，但同输入动作有差异 | 公开推理包尚未验收完成，不能只发 `.pt` 就称可用 |
| FastWAM 共用恢复权重 | 文件、step、配置、统计和 SHA256 已核对；原状态保存 30+30 个专家 blocks，剪枝依靠双专家的运行时 mask | 尚缺经过独立验证的公开推理包；不能称为物理缩小的 checkpoint |

StarVLA 的公开版本迁移需要把旧窗口配置转换为 `action_horizon=8`。在一个固定输入上，原实现重复运行误差为 0，而公开上游路径与原实现的归一化动作最大绝对差约为 **0.002518**。两边参数均完整匹配、形状均为 `(1,8,7)`，所以仅检查加载成功和形状是不够的。这个差异尚未归因为某个具体预处理或计算环节；也没有用它推断任务成功率变差。公开加载代码必须进一步核对，或保留经过审查的原推理实现。

FastWAM 的 `.pt` 需要与原始 L2–L7 删除集合、两个专家同时跳过的实现、数据统计和上游资产一起使用。当前检查只确认文件和结构，不代表已经在新环境完成推理。Long 是另外的五层配置，其记录路径下的权重仍缺失。

OFT 的 9/10 是 OSMesa 小规模检查，不替代论文的 463/500，也不声明采用独立于搜索的最终状态集。权重名称、大小、当前哈希、历史记录对应关系和公开下载的空缺都明确保存在索引中；没有虚构下载链接。

下载后使用 OFT 的入口已补齐：

```bash
python -m autoprune.eval_oft_export --exported /path/to/oft-object \
  --suite libero_object --trials 1 --max-eval-tasks 1 --run-root runs
```

这个入口不需要作者的原搜索目录、dense 模型、teacher cache、API key、RLDS 训练集或 HDF5 校准演示。它仍需要正确的 GPU 环境和完整 LIBERO 仿真资源。本轮在不继承旧 site-packages 的新环境、重新拉取的 OFT/LIBERO 中完成了实际评估，1/1。

## 用法二：读者拿自己的权重，接 API、输入指令，最后拿到 checkpoint

**对于兼容 OFT 的权重，或已经完成模型适配的架构，这条流程可以执行。** 对读者而言，需要先准备：

1. 能正确加载的权重及 tokenizer、动作头、归一化等完整模型资源。
2. 固定校准输入、恢复训练数据、任务评估环境和实测 dense baseline。
3. GPU、模型服务 API，以及训练/搜索预算。

然后在搜索命令上添加：

```bash
--export-to exports/my-model --verify-export
```

OFT 会依次查询实时探针、调用 API 选方案、训练、闭环评估，并在有达标方案时自动导出和独立重载。`--verify-export` 的现成数值检查针对 OFT；其他架构使用自己的 native verifier。

本轮在原环境和新建 GPU 环境分别用实际模型服务和 OFT 权重完成这个自动流程，终态为 `exported_and_action_verified`，导出前后动作误差 0。该检查采用一个真实演示的 24 帧、17 个 teacher 动作块、两步恢复、一次任务评估，并把测试成功率门槛明确设为 0。因此它验证自动交付衔接，**不证明两步模型具备任务效果，也不证明正常预算下一定达到 90%**。

没有达标方案时，程序会保存 `delivery.json`，状态为 `no_qualifying_checkpoint`、退出码 3，不把 Pareto 前沿的未达标模型当成通过。导出失败时保留搜索、训练和评估记录，明确记录失败。

新架构需要按 [ADDING_A_MODEL.md](ADDING_A_MODEL.md) 适配模型相关操作与 native saver。框架提供搜索算法、探针、反馈、选择和导出调度；适配是正常接入步骤。API 无法自动替代这部分，也不能提供训练数据或任务环境。

当前没有长搜索的自动断点恢复，也没有强制执行“几天内完成”的调度能力。结果取决于模型、恢复预算、评估次数、GPU 和任务可行性；即使程序正常跑完，也可能没有满足目标的方案。

## 从零安装实际发现的问题

本轮新建不继承旧模型依赖的 Python 3.10 环境，按安装脚本重新下载并安装依赖、OFT 和 LIBERO，并实际运行模型。发现并修复：

- 旧 pip 对 CUDA 下载源的依赖元数据处理失败：安装脚本先升级 pip。
- Flash Attention 2.5.5 的 wheel 安装在临时目录与持久缓存跨文件系统时发生 `EXDEV`：该安装步骤使用临时缓存；触发条件来自本次隔离缓存设在另一文件系统。
- `pip check` 虽通过，新版 tensorflow-metadata 的生成代码仍无法在 protobuf 4 下导入：固定到实际可用的 1.17.3，并在安装末尾增加 OFT 的真实导入检查。
- MuJoCo 原先没有版本约束，会解析到与本轮验收不同的物理引擎版本：固定本轮实际验证的 3.7.0，不把它冒充历史论文版本。

当前版本通过 **106 项测试**。测试数只表示软件回归范围；前面的真实权重评估、动作对照和新环境运行是另外的行为证据。

## 提示词与论文实现边界

修复了 `SR>=0.5%` 被当成 50%、英文 success-rate 表达未识别、常见删层数量表达未解析，以及“检查所有层”被误当成“运行所有 suite”的问题。启动时打印实际解析的门槛和预算，并保存到 `request.json`。

接受门槛建议使用明确的 `SR>=90%`、`成功率不低于90%`、`k>=8`、`k<=16` 或对应显式 CLI 参数。解析器仍是有限规则，不是任意自然语言约束的完整解释器。其他说明传给 LLM，但不能因此声称所有附加要求都被程序强制执行；有歧义的相对成功率下降表达明确拒绝。

论文对未知 recovery ID 描述了首项回退；当前候选采用严格校验、让 agent 修订，而非静默更换。这是已经记录的发布版行为差异，不能将新版搜索轨迹等同于历史轨迹。原数据、旧缓存、权重及实验源文件未被重写。

## 现有 GitHub 仓库不能直接切为公开

检查了发布分支可达历史、cyk 历史和另一旧分支的当前树，共 18 棵 commit 树、773 个不同 blob；读取并检查了 759 个文本 blob，14 个 blob 未完成文本读取，另有一个旧分支的更早历史未全量扫描。旧 main 的已提交脚本中发现一处非占位的凭据样式字面量，且属于发布分支的祖先。未尝试使用该值；报告不复制凭据。

因此即使当前发布目录已清理，也不能直接把这个私有仓库切成公开。应从本次审查的文件清单生成不带旧 `.git` 的干净源码包，保留原实验仓库私有，再由作者选定正式公开仓库与权重托管位置。持有者需要处理旧凭据；没有声称已撤销或已轮换。[GitHub 官方处理说明](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)也将撤销/轮换与历史清理分开。

## 发布建议

先把“核心框架 + 可执行 OFT 示例 + OFT 权重”作为明确的一期交付。StarVLA 和 FastWAM 的权重、loader、配置与独立验证齐全后，再声明它们可以下载即用。它们是作者自己的论文产物，提供参考组件不能替代完成权重使用包。

本次没有修改仓库可见性、重写旧历史、上传公共权重或启动完整论文复现。准备好的源码包和本地 OFT 模型仍需要作者决定最终托管位置；不能把这些发布动作写成已经完成。
